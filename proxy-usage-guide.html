1. What this proxy is

A local HTTP server that forwards Apigee Management API calls upstream, injecting credentials for you. You call it as if it were apigee.googleapis.com, minus the authentication work.

  • Path mapping is 1:1. http://localhost:8080/v1/organizations/… corresponds to https://apigee.googleapis.com/v1/organizations/….
  • No auth required locally. Requests succeed with no Authorization header. Sending a bogus bearer token still returns 200, so the proxy overrides client credentials with its own.
  • Responses are passed through essentially untouched — gzip, server: ESF, Google RPC error envelopes, and requestId trace details all arrive intact.
  • Read-mostly. Every GET works. Writes are gated (see Allowed methods).

Environments in this org

dev · dev2 · dev3 · sit · sit2 · sit3

Retrieve the current list at any time with GET /v1/organizations/gcp-pttep-th-it-apimgmt-dev/environments.

3. Allowed methods

MethodScopeStateNotes
GETAll pathsALLOWEDFully functional across every endpoint tested.
POST…/queriesALLOWEDEnabled Nov 2026. Creates async analytics query jobs.
POST…/analytics/exportsBLOCKEDReturns 405. Enable separately if you need data exports.
DELETEAll pathsBLOCKEDReturns 405. Cannot cancel or clean up query jobs.
PUT / PATCHAll pathsBLOCKEDReturns 405. The proxy cannot modify configuration.

A blocked method is rejected by the proxy itself, before Apigee is contacted:

HTTP/1.1 405 Method Not Allowed
Allow: GET

{
  "error": "method_not_allowed",
  "message": "The requested HTTP method is not allowed.",
  "allowedMethods": ["GET"]
}

This shape is distinct from Apigee's error envelope, which is the quickest way to tell "my proxy said no" from "Apigee said no".

Field name is metaData, not meta. Timestamps are epoch-millisecond strings, not ISO dates. revision is an array of strings even when there is only one revision.

5. Error responses

Two distinct error shapes reach you. Knowing which is which tells you where the problem lives.

ShapeOriginMeaning
{"error":"method_not_allowed",…} Your local proxy The method is not enabled. Apigee was never contacted.
{"error":{"code",…}} Apigee / Google The request was forwarded and rejected upstream. Read error.message.

Not found (404)

{
  "error": {
    "code": 404,
    "message": "generic::not_found: resource organizations/…/apis/foo not found",
    "status": "NOT_FOUND",
    "details": [
      { "@type": "type.googleapis.com/google.rpc.RequestInfo",
        "requestId": "17892784605342601227" }
    ]
  }
}

Permission denied (403)

Requesting a non-existent organization returns 403 PERMISSION_DENIED rather than 404. This is correct Apigee behavior — it deliberately does not disclose whether an org exists. Do not interpret a 403 as "my credentials are broken" without checking the org name first.

Keep details[].requestId when reporting problems. It is the only handle Google support can use to trace a specific call.

6. Analytics recipes

Apigee exposes analytics two ways, and they use different syntax for the same underlying data. This is the single biggest source of confusion.

EndpointGET …/stats/{dimension}POST …/queries
Best forQuick lookups, small resultsLarge reports, many rows
Metric syntaxselect=sum(message_count){"name":"message_count","function":"sum"}

ResultJSON inlineZIP + gzip artifact

6.1 Synchronous: /stats/{dimension}

curl -s -G "http://localhost:8080/v1/organizations/gcp-pttep-th-it-apimgmt-dev/environments/dev/stats/apis" \
  --data-urlencode "select=sum(message_count)" \
  --data-urlencode "timeUnit=day" \
  --data-urlencode "timeRange=11/22/2026 00:00~11/24/2026 23:59" \
  --data-urlencode "topk=3" \
  --data-urlencode "sortby=sum(message_count)"

Response shape groups values under environments[] → dimensions[] → metrics[] → values[]:

{
  "environments": [{
    "name": "dev",
    "dimensions": [{
      "name": "HR-WebServices",
      "metrics": [{
        "name": "sum(message_count)",
        "values": [
          { "timestamp": 1795478400000, "value": "3589" },
          { "timestamp": 1795392000000, "value": "9485" }
        ]
      }]
    }]
  }],
  "metaData": { … }
}

Parameter rules observed:

  • topk requires sortby. Omitting it fails: "sort columns must be specified for topk parameter".
  • Metric availability is per organization. response_time does not exist in this org's schema, producing "field \"response_time\" not present in schema of gcp-pttep-th-it-apimgmt-dev".
  • Query parameter values arrive intact and are validated server-side, so Apigee's validation messages are a reliable way to discover valid field names.
  • Verified dimensions: proxy, apis.

6.2 Asynchronous: POST /queries

Three steps: create, poll, download.

Step 1 — create

curl -s -X POST \
  "http://localhost:8080/v1/organizations/gcp-pttep-th-it-apimgmt-dev/environments/dev/queries" \
  -H "Content-Type: application/json" \
  -d '{
    "dimensions": ["proxy"],
    "metrics": [{ "name": "message_count", "function": "sum" }],
    "timeRange": { "start": "2026-11-17T00:00:00Z", "end": "2026-11-24T00:00:00Z" },
    "groupByTimeUnit": "day",
    "limit": 5
  }'
{
  "self": "/organizations/gcp-pttep-th-it-apimgmt-dev/environments/dev/queries/7cb64c22-…",
  "state": "enqueued",
  "created": "2026-11-24T04:12:13Z"
}

Request-body rules that will bite you

  • metrics[].name is the bare metric — "message_count". Writing "sum(message_count)" here is rejected. That bracket form belongs to /stats only.
  • timeRange.start / .end must be RFC 3339 with a T separator and zone. "2026-11-17 00:00:00" is rejected with a Go time-parse error.
  • The response is 200, not 201 or 202.

Step 2 — poll until completed

curl -s "http://localhost:8080/v1/organizations/gcp-pttep-th-it-apimgmt-dev/environments/dev/queries/{id}"
{
  "state": "completed",
  "result": {
    "self": "…/queries/{id}/result",
    "expires": "2026-11-30T20:12:25-08:00"
  },
  "resultRows": "5",
  "resultFileSize": "0.15 KB",
  "executionTime": "12 seconds",
  "queryParams": { … }
}

Observed state progression: enqueued → running → completed, taking about 12 seconds for a 5-row query. Poll every 3–5 seconds; do not spin.

Timezone quirk: the POST response renders created as UTC (…04:12:13Z) while subsequent GETs render the same instant as …20:12:13-08:00. Same moment, different notation — normalize before comparing or sorting.

7. Query result files

The result endpoint does not return JSON directly. It returns a ZIP archive containing a gzipped JSON file — two layers of compression.

content-type: application/octet-stream
content-disposition: attachment; filename="OfflineQueryResult-{id}.zip"

Inside the ZIP is QueryResults-{id}-000000000000.json.gz. Decompress both layers, then read newline-delimited JSON:

{"day":"2026-11-20 00:00:00 UTC","proxy":"admin","sum_message_count":"10"}
{"day":"2026-11-18 00:00:00 UTC","proxy":"insure","sum_message_count":"881"}
{"day":"2026-11-18 00:00:00 UTC","proxy":"new-cluster","sum_message_count":"2"}

PowerShell:

curl.exe -sS -o result.zip "http://localhost:8080/v1/organizations/{org}/environments/dev/queries/{id}/result"
Expand-Archive .\result.zip -DestinationPath .\result-out -Force
# then gunzip each *.gz inside .\result-out

Results expire 7 days after completion — result.expires tells you when. After that, fetching returns 400 INVALID_ARGUMENT with "query result expired on …". Download promptly; re-running the query is the only recovery.

Because DELETE is blocked on this proxy, query jobs cannot be cancelled or cleaned up manually. They age out on their own.

8. Calling it from shell tools

curl — recommended for anything with a body

curl -s "http://localhost:8080/v1/organizations/gcp-pttep-th-it-apimgmt-dev/apis"

curl -s -X POST "http://localhost:8080/v1/organizations/{org}/environments/dev/queries" \
  -H "Content-Type: application/json" --data-binary "@query-body.json"

--data-binary "@file" sends only Content-Length and works reliably.

PowerShell gotchas

  • Inline JSON in double quotes loses its quotes before reaching the executable, producing mangled payloads like {dimensions:[proxy]}. Prefer --data-binary "@file.json" in curl, or write the body to a file.
  • When using Postman CLI on Windows, pass --body @<ABSOLUTE-PATH>. A relative @file was read as empty during testing.

Postman CLI — know the limitation

Postman CLI v1.74.0 sends both Content-Length and Transfer-Encoding: chunked on POST bodies. That combination is ambiguous per RFC 7230, and this proxy ends up forwarding an empty body, so Apigee replies:

{ "error": { "code": 400,
  "message": "request body cannot be empty",
  "status": "INVALID_ARGUMENT" } }

The identical file through curl succeeds. Until one side is fixed, use curl for POSTs.

  • Proxy fix: honour Transfer-Encoding: chunked request bodies. A typical cause is copying the inbound Content-Length onto the outbound request instead of piping the inbound stream.
  • Client fix: run postman update (v1.93.1 was available at time of testing) and retest.

GET requests through Postman CLI work fine — this limitation is specific to request bodies.

9. Gotchas and limits

  • Analytics is slow. /stats takes 1.6–3.0 s versus ~0.6 s for management calls. Set timeouts to 30 s or more; 60 s for query creation and polling.
  • Exit codes are not health signals. Postman CLI returns 1 for any non-2xx, even when every assertion passed. Gate CI on assertion counts, not just the exit code.
  • Schema introspection is unreliable. /analytics/admin/schemav2 requires a type parameter and returned NOT_FOUND for api, env, and all on this org. Use validation error messages, or the Apigee console, to discover valid metric names.
  • /analytics/datastores returns 404 with an HTML body. That is an Edge-only API, absent from Apigee X. Not a proxy fault.
  • Two API generations coexist. /stats uses sum(metric) plus MM/DD/YYYY ranges; /queries uses bare metrics plus RFC 3339. Keep the two recipes separate in your code.
  • Trailing slashes are tolerated on collection paths (verified on /apis/), so do not rely on a 404 to detect a wrong path.

10. Security notes

The proxy is unauthenticated by design. Anyone or anything running on this machine can read the org's full proxy inventory and analytics through it. That is acceptable for a local development tool, and it is why the binding matters:

netstat confirms it listens on 127.0.0.1:8080 only — loopback, not the LAN. Do not rebind to 0.0.0.0 without adding authentication in front of it; the injected credentials are real and would be usable by anyone who can reach the port.

  • Client-supplied Authorization headers are overridden, not honoured. Do not design flows that depend on passing your own token through this proxy.
  • The proxy cannot mutate anything while writes are blocked, which sharply limits blast radius. If you enable POST /analytics/exports or DELETE, re-assess that.
  • Upstream connectivity and credentials come from the proxy's own configuration, not from the caller — a misconfigured proxy fails for every client at once.

11. Verifying the proxy

verify-proxy.js is a dependency-free Node script (Node 18+, uses built-in fetch) that walks the proxy's read paths and prints a verdict. It is read-only — no creates, updates, or deletes — so it is safe to run in CI on every build.

node verify-proxy.js
node verify-proxy.js http://localhost:8080
BASE_URL=http://localhost:8080 ORG=gcp-pttep-th-it-apimgmt-dev ENV=dev node verify-proxy.js
NO_COLOR=1 node verify-proxy.js

Why some checks warn instead of fail. A 403 on a missing resource and a 400 on a metric name are both correct Apigee behavior, not proxy faults. Failing on them would produce noise and train you to ignore the script. Only conditions that actually indicate a broken proxy return FAIL.

Exit codes and configuration

0 when every check passes, 1 if anything failed. Warnings do not affect the exit code. Configuration comes from arguments or environment variables:
